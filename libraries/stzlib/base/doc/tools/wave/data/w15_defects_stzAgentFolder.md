# Wave 15, group 4 -- defects found while documenting (not fixed; comments only)

Format: class.method: symptom: cause: evidence.

## agentic

- stzAgentMemory.Restore: Save("mem") then Restore("mem") raises error R13 Object is required, in `_mergeknowledgebase` of stzKnowledgeGraph: Save goes through `WriteToKnowFile`, which appends `.zknw` when the name lacks it, while Restore goes through `ImportKnow`, which reads a string that does not end in `.zknw` or `.stzknow` as the TEXT of a knowledge file. The two halves of a round trip disagree about the file name. Evidence: Save of `.../mem3` wrote `mem3.zknw`; Restore of `.../mem3` raised R13; Restore of `.../mem2.zknw` (saved with the extension) merged 2 facts with provenance. Documented as a warning on Save and Restore.
- stzAgentMemory.Restore: the `merged` count counts the facts read, not the facts added: restoring the same file twice into one memory answers merged 2 both times while the memory holds 2 facts. Minor; noted on Restore.
- stzLLMAgent.Propose: the error raised when no body is set reads "SkillFrom(anStzLLMFunction) first", but the method is SetSkillFrom. Cosmetic; noted on Propose.

## i18n

- stzCurrency.init: building from a currency name (euro, west_african_cfa_franc), a symbol (XOF) or a locale abbreviation (fr-NE) does not work. Cause: `stzString.IsCurrencyName` compares against `CurrenciesXT()[1]`, which is the COUNTRY column of `CountriesOrRegionsAndTheirCurrenciesXT`, so a currency name is never recognised (and a country name is, but the country branch is tried first); `IsCurrencySymbol` is a stub that answers 0; the locale-abbreviation branch is an empty `// TODO`. The refusal then calls `stzCurrencyError`, which lives in base/error/stzCurrencyError.ring and is not loaded, so the user sees R3 "Calling Function without definition: stzcurrencyerror". Evidence: `new stzCurrency("euro")`, `("XOF")`, `("west_african_cfa_franc")` all raise R3; `("fr-NE")` builds an object whose Currency() answers N (the first letter of the empty attribute); `("niger")` and `("united_states")` work. Documented as a warning on init.
- stzLanguage.init: an unknown identifier raises R3 "stzlanguageerror" (same cause: error function not loaded); `fr-FR` raises "Feature not yet implemented!". A country name selects the first language whose default country it is (France gives breton, Niger gives zarma). Documented.
- stzLanguage.EngineField and EngineFieldByAbbr: raise R3 today; they call `StzEngineRefLanguageField` and `StzEngineRefLanguageFieldByAbbr`, defined nowhere in the library (grep over base). Evidence: `new stzLanguage("French").EngineField("native")` and `.EngineFieldByAbbr("native")`.
- stzLanguage.DefaultScript / DefaultScriptNumber / Scripts / ScriptsAbbreviations: French answers duployan, not latin. Cause: the methods search the script table for rows whose default-language column is the language, and the table gives each script ONE default language (latin -> english), so most languages match the wrong, minor script or none. Evidence: French -> [ duployan ], Hausa -> [ boko ], Arabic -> [ arabic ]. Documented as a warning.
- stzScript.Languages: the default language is not always in the list (boko: DefaultLanguage hausa, Languages empty); names there carry no separators (judeospanish) while DefaultLanguage answers underscored names (standard_morocco_tamazight). Documented.

## learning

- stzNeuralNetwork.Predict: an input SHORTER than the network takes is accepted silently (the missing values contribute nothing) and answers a number; a LONGER one raises R2 Array Access (Index out of range). Neither is validated, unlike stzTrainer.Train, which names the width. Evidence: a 2-input network answered [ 0.22 ] for [1] and raised R2 for [1,2,3]. Documented as a warning on Predict.
- stzDecisionTree / stzKnn: the training set handed to the constructor is copied (Ring copy-on-assign), so growing the caller's own object afterwards does not reach the learner; the classes say so themselves and expose TrainingSetQ for the live set. Documented, not a defect.

## meta

- stzPredicateSet.Seal / Verify (security-relevant): the seal is an UNKEYED SHA-256 of the body. A file whose rules are edited and whose seal line is recomputed verifies TRUE (tested: a set rebuilt with engine-first and saved verifies after LoadFrom). So Verify detects a silent edit, and does not authenticate who wrote the file; the header comment says "a reviewer signs the seal" but nothing in the class signs. Documented as a warning on Seal and Verify; the fix (a keyed MAC or a signature check) belongs to the security desk.
- stzPredicateSet.LoadFrom: the file's rules and invariants are checked against the library's lists (an unknown name raises the unknown-rule error), so a file cannot inject a rule; LoadFrom does not clear the rules already held, and Save adds the extension .zrlz while LoadFrom does not (LoadFrom of the name given to Save raises the file error R35). Documented.
- stzPyCodeGraph.ScanSourceViaAst: NOT RUN while documenting (it spawns a system Python); read from the code only.
- stzSelfDoc.BestMethodFor / HowTo: retrieval is by shared words, so "check the precondition" on stzAgentSkill answers init instead of PreconditionHolds. Not a code defect, noted on BestMethodFor.

## network

- stzWebSocket (whole class): Connect raises R3 "Calling Function without definition: curl_easy_init". The class still wraps libcurl (curl_easy_init, curl_easy_setopt_*, curl_ws_send, curl_ws_recv, curl_easy_cleanup), which the library no longer loads since the network layer moved to the engine (M-DEP3/4). Even with libcurl present, `_curl_handle_` is a local of Connect, so SendText, SendBinary, Receive and Close could not see it. Evidence: `new stzWebSocket().Connect("ws://127.0.0.1:9/x")` raises R3 (no socket is opened: the call fails before any I/O); isfunction("curl_easy_init") and ("curl_ws_send") answer 0. The unconnected calls answer "Not connected". Documented class-wide as a warning.
- stzTcpServer.Listen: security-relevant. (1) An empty host means 0.0.0.0, every interface. (2) On this Windows machine a second stzTcpServer listening on the same loopback port as a live listener reported IsListening 1 with no error (tested: two servers on 47313), so a process can bind a port another process already serves. Cause not isolated (probably SO_REUSEADDR in the engine's listen); the engine owner should check. Documented as a warning on Listen.
- stzTcpServer.OnClientDisconnect / OnClientMessage: the callbacks are stored and never called. Documented.
- stzTcpClient.LocalAddress / RemoteAddress: fixed placeholders "127.0.0.1" and "0.0.0.0", whatever the connection. Documented.
- stzTcpClient.Receive / ReceiveWithMax / stzTcpServer.AcceptOne: block for ever with no timeout when nothing arrives (the first probe of this wave hung on it and the Ring process was stopped by its PID). Documented.
- Callback names: OnClose (a name the library defines as a function with parameters) given as a callback name fails with R19 "less number of parameters" at Close; a distinct name works. Noted on OnConnect.

## security

- stzPasskeyServer.VerifyAssertion / RegisterCredential (FAIL-OPEN, security-relevant): an EMPTY expected challenge skips the challenge check, and a server built with an EMPTY origin skips the origin check. Evidence (stzPasskeySandbox, real P-256 keys): a valid assertion for challenge c2 verified (ok 1) when the caller passed "" as the expected challenge, i.e. a captured assertion replays; and `new stzPasskeyServer("example.com", "")` accepted an assertion signed for https://evil.example (ok 1), while the same assertion is refused (ok 0) once the origin is set. Cause: `_ClientDataIsSound` guards both comparisons with `if expected != ""` and `if @cOrigin != ""`. A caller that loses the stored challenge (a session bug) therefore fails open instead of closed. Documented as warnings on init, SetOrigin, RegisterCredential and VerifyAssertion; the fix (refuse when either is empty) belongs to the security desk.
- stzPasskeyServer.Why / the noted refusal: the origin from the browser's client data is written into the reason and into the ledger unescaped (origin mismatch: 'https://a<script>x()</script>.example' is not ...). A client-data origin holding angle brackets (JSON-valid, quote-free) is reflected verbatim; an app that puts Why in a page gets markup injection. Documented as a warning on Why.
- stzPasskeySandbox.ClientData: builds the client-data JSON by plain concatenation, so a challenge or origin holding a quote adds or duplicates keys (tested: a challenge ending in `abc","origin":"https://evil.example` produced two "origin" keys). A test double, so low risk, but a test may pass for the wrong reason. Documented. Also, Assert advances SignCount before it checks that a credential exists, so an Assert that raises still counts one.
- stzRequestSigner.Verify (log content, security-relevant): the ledger note carries "path:" + the full path INCLUDING its query string, so a token placed in a query string (tested: /p?token=SECRETVALUE) is written to the security ledger and shows in its text view; and an unknown key id is written raw to the actor and reason fields, line breaks included (tested: a key id holding a newline and FAKE-LINE shows a forged second line in the ledger's Show text). The stored record is a list of fields, so the chain is intact; the text rendering is what forges. Documented as warnings on Verify and Why.
- stzSecurityAttestation.Explain: states "entries are DESCRIPTORS -- no secret value is present in this evidence by construction", which holds for values the library describes but not for what a caller put in an event subject (the query-string token above reaches an exported evidence file). Documented as a note on Explain.
- stzApiKey.AuthorizationHeader: builds "Bearer " + the value with no check for CR or LF, so a value read from a file with a trailing newline (or a hostile value) yields a header with an extra line (tested with an invented value holding CRLF and X-Injected: 1). Documented as a warning.
- stzTotp.Show prints the shared secret in clear (and Secret / ProvisioningUri carry it by design). stzTotp.Verify and VerifyAt do not consume a code: the same code verifies repeatedly inside its window (tested: VerifyAt twice, both 1). Documented; the caller must remember the last accepted step.
- stzVaultHttpResolver: with no answer (connection refused, or a timeout against a loopback port that never answered) the status is -1 and the error reads "Vault answered -1 for ..." because the "Vault did not answer at ..." branch tests status 0. The locator is appended to the URL as given (no encoding, no rejection of ../ or ?), so a locator built from untrusted input can steer the request, with the token, to another path of the same server; and it is quoted unescaped in errors. The address check itself is sound (tested 13 addresses, including http://127.0.0.1@evil.example and http://localhost.evil.example, which are refused). Documented. Not run against a real vault.
- stzPredicateSet (see meta): unkeyed seal.

## service

- stzOidcSandbox.IssueIdToken / IssueIdTokenAt / IssueIdTokenXT (token injection, security-relevant, a TEST DOUBLE): the subject, nonce, issuer, audience and email are written into the signed payload JSON by plain concatenation, with no escaping. Evidence: IssueIdToken('dana","admin":true,"x":"', ...) produced a payload with `"sub":"dana","admin":true,"x":""` and a second `"email":"dana","admin":true,"x":"@idp.local"` -- extra and duplicated claims under a REAL signature. The same holds for the kid and issuer in JwksJson and DiscoveryJson (a kid of `k"},{"kid":"evil` produced a second key entry). Because a sandbox's job is to be fed test data this is not exploitable by itself, but the file is the only model in the library of how an id token is built, and a real issuer copying it would inject claims; a test can also pass for the wrong reason. Documented as warnings on init, SetKeyId, JwksJson, DiscoveryJson, IssueIdToken and IssueIdTokenAt.
- stzSmsSandbox.Send: the rejection reason quotes the number as given, unescaped (`'+1"><script>x()</script>' is not an E.164 number`). Documented.
- stzMailSandbox.Send: no validation, so a header-injection recipient or subject (CRLF) is captured and "passes"; the sandbox cannot warn that a real adapter must refuse it. Documented.
- stzSqliteDataSource.RowCount: a table whose name needs quoting (my-table) raises a SQL syntax error because the name is put bare into the query once TableExists has confirmed it; a table-name string holding SQL answers 0 and runs nothing (tested: RowCount("people; DROP TABLE people") left people intact). Documented as a warning. After Close, Exec raises "SQL error: " with an empty cause while Rows and Value raise "no such database handle". Documented.
