# golden_v34: first NON-Chrome golden set

This set has 24 realistic documents (`x01` to `x24`), each a PDF with an `.expected.json` and a one-line `.src.txt`.
Unlike every earlier set, **no PDF here was made with Chrome, Edge or any browser**. The point is to test document readers on files
from other producers, the way real files arrive: ReportLab (Platypus and the low-level canvas), PyMuPDF (Story/HTML and
`insert_text`/`draw_*`), matplotlib (Type 42 and Type 3 fonts) and Windows "Microsoft Print to PDF" (a GDI print path driven
silently from PowerShell; no dialog was needed). Every `/Producer` entry was checked in the raw bytes: none names Chrome, Skia or Edge.

## How it was made

Each document is generated by a Python script that holds the content once and, while drawing it, appends the same text to the expected
structure, so the expected text is the text drawn. The generators live outside the repository (a private scratch folder) and are not part of the set.
For the GDI documents the script writes a JSON list of draw operations that a small PowerShell program replays on `System.Drawing.Printing.PrintDocument`
(printer "Microsoft Print to PDF", print to file); the author wrapped the lines with font metrics, the driver does not wrap.

Checks that were run, all on raw bytes or font tables and never on rendered output:

- page counts from the raw PDF bytes (`/Type /Page`, `/Count`) equal `pages` in every `.expected.json`;
- every character of every expected string exists in the TrueType font it is drawn in (fontTools cmap), or in cp1252 (ReportLab standard-14) or Latin-1 (PyMuPDF base-14, whose `insert_text` cannot draw anything above U+00FF);
- fonts embedded versus standard-14 were read from raw `/BaseFont` and `/FontFile*` entries.

## Honesty statement

The author of this set **never ran, imported for reading or looked at any PDF-to-text or document-conversion tool, text-extraction function, rasterizer or renderer**,
and never saw a reader's code or output, `golden_v1` to `golden_v33`, or any results file. PyMuPDF was used only to write. The author never looked at the pages either:
**every document is UNPERCEIVED** (nobody has looked at it yet). That matters most for the right-to-left files (`x15`, `x16`, `x21`), where shaping and ordering were done by MuPDF's HTML engine or by GDI+ and
were not seen, and for line wraps, which were computed from font metrics. A scorer disagreeing with an expected file on one of those points should settle it by looking at the page.

## Conventions used in the expected files

- Key/value forms are recorded as tables **without a header row** (rows are `[label, value]`; labels keep a drawn colon). Their notes say so.
- A merged cell repeats its text in every grid cell it covers (totals rows and section rows that span columns). A table continued over a page is ONE table with its header row once.
- Right-to-left tables list cells in logical order, rightmost column first. MuPDF does not mirror HTML tables, so in `x15` and `x16` the cells were emitted last-to-first to put the first logical column at the right edge.
- Lists keep the marker in the text when it is typed (bullet, `-`, `1.`, `1)`, `(a)`, Arabic, Hebrew, Greek and Korean letters); check boxes and bullets that are drawn shapes (`x10`, `x12`) carry no marker.
- Where a document has more than ten body sentences, the file lists ten of them, evenly spaced, in reading order.
- Letter metadata (date, addressee, sign-off) and front matter such as authors are listed in no field; each `notes` says so.
- ReportLab documents with TrueType fonts also list the default `Helvetica` in their font resources; no text is drawn with it.
