Ledgerline Server 4.2.0 release notes

Released 14 October 2026 · supersedes 4.1.3

Ledgerline Server 4.2.0 introduces scheduled reconciliation, faster ledger exports and stricter TLS defaults. Most installations can upgrade in place in under fifteen minutes, but one configuration key has been renamed.

Highlights

  • Reconciliation jobs can now run on a fixed interval instead of only on demand.
  • CSV and Parquet exports of large ledgers are about three times faster.
  • TLS 1.3 is the default minimum version for the HTTP listener.
  • The audit log records the client certificate fingerprint for every write.

Breaking changes

The server refuses to start if the old key reconcile_every is still present in the configuration file. Rename it before restarting, as shown in step 2 of the runbook.

Clients that only support TLS 1.2 will fail to connect after the upgrade unless tls_min_version is set back to "1.2".

Upgrade runbook

Run these steps on each application node in turn. A single-node installation will be unavailable for the duration of steps 1 to 3.

Step 1: Back up and stop the service

$ ledgerctl backup create --label pre-4.2 --verify
$ sudo systemctl stop ledgerline
$ sudo apt-get install ledgerline-server=4.2.0-1

Step 2: Update the configuration

Edit the server configuration and rename the reconciliation key. The other keys below are shown for context.

# /etc/ledgerline/server.yaml
database:
  url: postgres://ledger@db01:5432/ledger
  pool_size: 20
http:
  listen: 0.0.0.0:8443
  tls_min_version: "1.3"
jobs:
  reconcile_interval: 15m   # was reconcile_every in 4.1

Step 3: Migrate and start

$ ledgerctl migrate --check
$ ledgerctl migrate --apply
$ sudo systemctl start ledgerline
$ curl -fsS https://localhost:8443/healthz
{"status":"ready","version":"4.2.0"}

The migration adds two indexes to the journal table and takes about one minute per ten million journal lines.

Rollback

If the health check fails, stop the service, reinstall version 4.1.3 and restore the backup taken in step 1. Do not run the 4.1 server against a database that has been migrated to 4.2.
