Tidewater API 4.2 Release Notes

Released 9 March 2026 · Applies to all hosted and self managed installations

Version 4.2 introduces batch uploads, a new rate limit header and several fixes to webhook delivery. Two older endpoints are deprecated and will be removed in version 5.0. Please read the breaking changes section before upgrading a production system.

Highlights

  • Batch uploads of up to 500 records in a single request
    • Partial failures are reported per record
    • Each batch returns a job identifier
      • Jobs can be polled or followed by webhook
  • A new header reports the remaining request allowance
  • Webhook retries now follow an exponential schedule

Breaking changes

Timestamps in all responses are now returned in UTC with an explicit offset. Clients that parse local time strings must be updated before the upgrade.

New features

Batch uploads

Send an array of records to the batch endpoint. The response contains a job identifier and the number of records accepted.

{
  "job_id": "job_7f3a91",
  "accepted": 498,
  "rejected": 2,
  "status": "queued"
}

Rate limit header

Every response now carries a header with the number of requests left in the current window. The window length is sixty seconds for all plans.

Deprecations

The following endpoints still work in version 4.2 but return a deprecation warning.

EndpointReplacementRemoval
POST /v3/records/importPOST /v4/records/batchVersion 5.0
GET /v3/events/streamWebhook subscriptionsVersion 5.0

Fixed issues

  • Webhooks were sometimes delivered twice after a network timeout.
  • Search results ignored the page size parameter above 100.
    • The limit is now enforced at 250 results per page.
  • Exports of empty collections returned an error instead of an empty file.

Upgrade guide

  1. Back up the configuration directory.
  2. Pull the new image and restart the service.
  3. Update the client settings shown below.
docker pull registry.tidewater.example/api:4.2.0
docker compose up -d api
client:
  api_version: "4.2"
  timestamps: utc
  retry:
    max_attempts: 5
    backoff: exponential

After the upgrade, check the service log for deprecation warnings during the first day of traffic. Contact support if any client fails to parse the new timestamp format.
