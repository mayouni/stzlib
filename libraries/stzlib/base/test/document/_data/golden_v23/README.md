# golden_v23 -- 24 realistic PDF documents with known structure

An independent golden set for scoring document readers (Docling and Softanza's native PDF reader). Each document `fNN` has three files: `fNN.html` (the source), `fNN.pdf` (the rendered document) and `fNN.expected.json` (the structure a reader should recover).

## How it was made

- Every document was written as a small Python builder in the author's scratch folder, outside this repository. One helper call emits the HTML **and** records the same string into the expected structure, so the expected text and the visible text come from one source.
- Each HTML was printed to PDF by headless Chrome 156 (`--headless=new --disable-gpu --no-pdf-header-footer`, a separate `--user-data-dir` profile, `--print-to-pdf`). Page size A4; f13 is A4 landscape. Documents with running headers, footers or page numbers lay out each page as a fixed A4 box in the body (`@page { margin: 0 }`); the others use `@page { size: A4; margin: ... }` and natural flow.
- Checks run on every document: (1) every font family named in the CSS is installed in `C:\Windows\Fonts` and is static, not a variable font; (2) every character of every text run exists in the cmap of the font it is set in (computed style read from Chrome's DOM, then checked with fontTools); (3) no fixed page box overflows; (4) every expected string occurs in the page's DOM text (whitespace ignored), which catches CSS that changes visible text; (5) from the raw PDF bytes: the page count (`/Type /Page` objects equal `/Count`) and the embedded `/BaseFont` names, which must equal the fonts the DOM says were used. No fallback font was embedded in any document.
- The author **never ran a PDF-to-text extractor, document converter or PDF rasterizer**, never looked at any reader's code or output, and never opened golden_v1 to golden_v22. Visual checks were screenshots of the HTML in headless Chrome, never rasters of the PDFs. The PDFs were read only as raw bytes, for `/BaseFont`, `/Type /Page` and `/Count`.
- All organisations, people, addresses, numbers and e-mail domains (`.example`) are fictional.

## Conventions of expected.json

- Keys: `id, difficulty, pages, title, headings, key_sentences, tables, list_items, furniture, languages, code, notes`.
- Text is NFC; whitespace runs collapse to one space (non-breaking spaces count as spaces); code keeps its whitespace.
- In scripts written without spaces (ja, zh, th) a line wrapped inside a sentence joins with no space.
- Right-to-left text and tables are in logical order; a right-to-left table lists the rightmost column first.
- Tables: header row(s) first; merged cells repeat their text in every grid cell they cover; a multi-line cell is joined with one space; totals and section rows are rows of the same table; a table continued across pages is one table with its header row once.
- Lists: a TYPED marker is part of the item text, followed by one space (CJK full-width markers and the Japanese "・" are followed by no space); a marker drawn by CSS (`list-style`) is not in the text. Level 0 is the outermost level. Each document's notes say which markers are typed and which CSS draws.
- Furniture: one visible line per entry; a repeated running header or footer once; page-number lines once per page. Blocks at opposite ends of one header or footer line are separate entries. A letterhead organisation name is furniture, never a heading.
- Key sentences: 4 to 10 full body sentences in reading order; a sentence carrying a footnote marker is never one.
- Boxes or columns set side by side and read box by box are named in the notes of the document concerned.
